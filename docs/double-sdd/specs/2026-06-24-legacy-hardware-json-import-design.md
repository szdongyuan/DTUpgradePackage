# Legacy Hardware JSON Import Design

## Purpose

Extend `create_hardware_tables.py` so that, after creating `hardware_assets` and `hardware_channel_calibrations`, it imports legacy selected-device and microphone calibration JSON data from the current working directory.

The script remains an independent database preparation/migration utility. It is not a runtime auto-upgrade path for the main application.

## Scope

In scope:

- Keep creating the two hardware tables in `database/system_data.db`.
- After table creation, read legacy files under `ui/ui_config` relative to the current working directory:
  - `last_audio_devices.json`
  - `mic_channel_calibration.json`
- If `mic_channel_calibration.json` is absent, accept `mic_channel_calibration.josn` as a compatibility fallback for the previously misspelled filename.
- Import microphone and speaker records from `last_audio_devices.json` into `hardware_assets`.
- Create channel placeholder rows in `hardware_channel_calibrations`.
- Sync existing microphone calibration values from the calibration JSON into the microphone input channel row.
- Print a Chinese warning telling the user that the imported microphone and speaker registration information is incomplete and recommending re-registration.
- Keep missing JSON files non-fatal: create the tables, print a Chinese warning, skip the missing import part, and exit successfully.
- Keep the import safe to re-run without creating duplicate legacy-import rows.

Out of scope:

- Importing output/speaker calibration values.
- Editing the existing application runtime hardware management flow.
- Updating `system_info_table` version values.
- Creating `database/system_data.db` when it is missing.
- Rebuilding executable artifacts.
- Writing back to either JSON file.

## Source Files

The script uses paths relative to the process current working directory:

```text
database/system_data.db
ui/ui_config/last_audio_devices.json
ui/ui_config/mic_channel_calibration.json
```

Fallback calibration filename:

```text
ui/ui_config/mic_channel_calibration.josn
```

## Legacy Selected Device Format

Expected `last_audio_devices.json` shape:

```json
{
  "mic": {
    "name": "麦克风 (6- High Definition Audio D",
    "hostapi_name": "MME",
    "default_samplerate": 44100.0
  },
  "speaker": {
    "name": "扬声器 (6- High Definition Audio D",
    "hostapi_name": "MME",
    "default_samplerate": 44100.0
  },
  "mic_channels": [0]
}
```

Only `mic`, `speaker`, and `mic_channels` are read. Runtime sounddevice indexes are not required and are not persisted into the database.

## Legacy Calibration Format

Expected `mic_channel_calibration.json` shape:

```json
{
  "version": 1,
  "channels": {
    "0": {
      "v2pa_factor": 1.0916916788093647,
      "calibrated_at": "2026-05-29",
      "standard_spl": 94
    }
  }
}
```

Only `channels` is required for calibration import. `calibrated_at` has no dedicated database column and remains preserved inside `coefficients_json`.

## Imported Hardware Rows

The import follows these hardware-management field meanings:

- `hardware_type` classifies the registered device as `microphone`, `speaker`, `audio_interface`, or `other`.
- `bit_depth` defaults to `32` for registration-style imports.
- `latency_ms` defaults to `100` for registration-style imports.
- Input channel labels use `In1..InN`.
- Output channel labels use `Out1..OutN`.
- Calibration fields are latest-payload fields for a channel row, not historical calibration records.
- Hardware and channel identifiers are UUID strings generated by application code.

### IDs

Normal hardware management registration uses UUID strings. This legacy import also stores UUID strings, but they are deterministic UUIDv5 values so repeated script runs update the same imported rows instead of creating duplicates.

UUID namespace:

```text
7d65144d-3935-5ca8-9f30-3f6ea9e62324
```

Stable IDs:

- Microphone `hardware_id`: UUIDv5 from `legacy-hardware-json:mic:<hostapi_name>:<name>`.
- Speaker `hardware_id`: UUIDv5 from `legacy-hardware-json:speaker:<hostapi_name>:<name>`.
- Channel `channel_id`: UUIDv5 from `legacy-hardware-json:<hardware_id>:<direction>:<channel_index>`.

The script uses `INSERT ... ON CONFLICT(...) DO UPDATE` for imported legacy rows.

Hardware asset upsert contract:

- Conflict target: `hardware_assets.hardware_id`.
- On conflict, update:
  - `hardware_type`
  - `display_name`
  - `device_name`
  - `hostapi_name`
  - `samplerate`
  - `bit_depth`
  - `latency_ms`
  - `max_input_channels`
  - `max_output_channels`
  - `updated_at = DATETIME('now', '+8 hours')`

Channel upsert contract:

- Conflict target: `hardware_channel_calibrations.channel_id`.
- Placeholder upserts update only identity/label fields:
  - `hardware_id`
  - `direction`
  - `channel_index`
  - `channel_label`
  - `updated_at = DATETIME('now', '+8 hours')`
- Placeholder upserts must not clear or overwrite existing calibration payload fields:
  - `calibration_type`
  - `factor_value`
  - `standard_spl`
  - `max_voltage`
  - `coefficients_json`
- A separate calibration sync update may overwrite calibration payload fields only when a valid channel `0` calibration object is present.

### Microphone Asset Mapping

If `last_audio_devices.json` contains a usable `mic` object:

- `hardware_type = "microphone"`
- `display_name = mic.name`
- `device_name = mic.name`
- `hostapi_name = mic.hostapi_name`
- `samplerate = int(mic.default_samplerate)` when it is `44100` or `48000`; otherwise `48000`
- `bit_depth = 32`
- `latency_ms = 100`
- `max_input_channels = 1`
- `max_output_channels = 0`

The script does not infer microphone input count from `mic_channels`; per user requirement it always imports the legacy microphone as one input channel.

### Speaker Asset Mapping

If `last_audio_devices.json` contains a usable `speaker` object:

- `hardware_type = "speaker"`
- `display_name = speaker.name`
- `device_name = speaker.name`
- `hostapi_name = speaker.hostapi_name`
- `samplerate = int(speaker.default_samplerate)` when it is `44100` or `48000`; otherwise `48000`
- `bit_depth = 32`
- `latency_ms = 100`
- `max_input_channels = 0`
- `max_output_channels = 1`

Per user requirement, the legacy speaker is always imported as one output channel.

## Imported Channel Rows

### Microphone Placeholder

When a microphone asset is imported, the script creates or updates one microphone channel row:

- `hardware_id = <microphone hardware_id>`
- `direction = "input"`
- `channel_index = 0`
- `channel_label = "In1"`
- `calibration_type = NULL` unless calibration JSON contains channel `0`
- `factor_value = NULL` unless calibration JSON contains channel `0`
- `standard_spl = NULL` unless calibration JSON contains channel `0`
- `max_voltage = NULL`
- `coefficients_json = NULL` unless calibration JSON contains channel `0`

On rerun, if the channel row already exists and no valid channel `0` calibration is available, these calibration fields are preserved as-is rather than reset to `NULL`.

### Speaker Placeholder

When a speaker asset is imported, the script creates or updates one speaker channel row:

- `hardware_id = <speaker hardware_id>`
- `direction = "output"`
- `channel_index = 0`
- `channel_label = "Out1"`
- `calibration_type = NULL`
- `factor_value = NULL`
- `standard_spl = NULL`
- `max_voltage = NULL`
- `coefficients_json = NULL`

These `NULL` calibration values apply only when the speaker channel row is first inserted. On rerun, if the speaker channel row already exists, the placeholder upsert preserves existing calibration payload fields rather than resetting them to `NULL`.

## Calibration Sync

If a calibration JSON file exists and contains `channels["0"]`, and a microphone asset is available, the script updates the microphone input channel row:

- `calibration_type = "v2pa"`
- `factor_value = channels["0"].v2pa_factor`
- `standard_spl = channels["0"].standard_spl`
- `max_voltage = NULL`
- `coefficients_json = JSON string of the original channel `0` calibration object, preserving non-column fields such as `calibrated_at`

Calibration channels other than `0` are ignored because the legacy import intentionally registers the microphone with `max_input_channels = 1`. If ignored channels exist, the script prints a Chinese warning.

If no calibration JSON exists, or if the calibration JSON exists but does not contain a usable `channels["0"]` object, calibration sync is skipped and any existing database calibration payload fields are preserved.

Calibration edge cases:

- If `channels` is missing or is not a JSON object, calibration sync is skipped, a Chinese warning is printed, and the script exits successfully.
- If `channels["0"]` is missing, calibration sync is skipped, a Chinese warning is printed, and the script exits successfully.
- If `channels["0"]` exists but is not a JSON object, calibration sync is skipped, a Chinese warning is printed, and the script exits successfully.
- If `channels["0"].v2pa_factor` is missing or non-numeric, calibration sync is skipped, a Chinese warning is printed, and the script exits successfully.
- If `channels["0"].standard_spl` is missing or non-numeric, calibration sync is skipped, a Chinese warning is printed, and the script exits successfully.
- These calibration-content issues are not fatal because the script can still create tables and import hardware assets safely.

## Missing Or Incomplete Data Behavior

Missing `database/system_data.db` remains fatal and exits with code `1`, matching the existing script behavior.

Missing JSON files are non-fatal:

- If `last_audio_devices.json` is missing, the script creates the tables, prints a Chinese warning, skips hardware import, and exits with code `0`.
- If calibration JSON is missing, the script imports hardware rows and channel placeholders, prints a Chinese warning, skips calibration sync, and exits with code `0`.

Incomplete JSON sections are non-fatal:

- If `mic` is missing or lacks `name` or `hostapi_name`, microphone import is skipped and a Chinese warning is printed.
- If `speaker` is missing or lacks `name` or `hostapi_name`, speaker import is skipped and a Chinese warning is printed.
- If `default_samplerate` is missing or unsupported, `samplerate` falls back to `48000` and a Chinese warning is printed.

Malformed JSON files are fatal:

- If a present JSON file cannot be parsed, the script rolls back the current transaction, prints a Chinese failure message, and exits with code `1`.

## Required User Warning

Whenever the script imports both microphone and speaker from `last_audio_devices.json`, it prints:

```text
警告：已根据旧配置文件导入麦克风和扬声器，但硬件注册信息不完整，麦克风输入通道数按 1 处理，扬声器输出通道数按 1 处理，建议在硬件管理中重新注册麦克风和扬声器。
```

If only the microphone is imported, it prints:

```text
警告：已根据旧配置文件导入麦克风，但硬件注册信息不完整，麦克风输入通道数按 1 处理，建议在硬件管理中重新注册麦克风。
```

If only the speaker is imported, it prints:

```text
警告：已根据旧配置文件导入扬声器，但硬件注册信息不完整，扬声器输出通道数按 1 处理，建议在硬件管理中重新注册扬声器。
```

If one side is skipped because it is missing or incomplete, an additional warning identifies the skipped side.

## Transaction Behavior

The script performs table creation and JSON import using a SQLite connection with `PRAGMA foreign_keys = ON`.

Database writes for one run are transactional:

- If table creation or import SQL fails, the transaction rolls back.
- If a present JSON file is malformed, the transaction rolls back.
- Missing optional JSON files do not trigger rollback.

Repeated runs must not duplicate the legacy-import hardware rows or their channel rows.

## Compatibility / Migration

Backward compatibility: partial.

Protected surfaces:

- Existing `database/system_data.db` data.
- Existing table creation behavior.
- Existing application runtime hardware management and selection flows.
- Existing `last_audio_devices.json` and `mic_channel_calibration.json` file contents.
- Existing database version metadata.

Allowed breakage:

- None for existing database rows.
- Malformed present JSON files may fail the script and roll back that run.

Migration strategy: standalone migration script.

This script performs an explicit, operator-run import from legacy JSON into the new hardware tables. The main application must not silently perform this import at startup.

## Testing

Automated tests should cover:

- Tables are still created when both legacy JSON files are missing.
- Missing JSON files produce Chinese warnings and do not fail the script.
- A valid `last_audio_devices.json` imports one microphone asset and one speaker asset using the required default values.
- The imported microphone has `max_input_channels = 1`.
- The imported speaker has `max_output_channels = 1`.
- The imported microphone channel row uses `direction = "input"` and `channel_label = "In1"`.
- The imported speaker channel row uses `direction = "output"` and `channel_label = "Out1"`.
- Re-running the import updates the same deterministic UUID rows and does not create duplicates.
- A valid calibration JSON updates the microphone input channel row with `calibration_type = "v2pa"`, `factor_value`, `standard_spl`, and `coefficients_json`.
- Re-running after removing calibration JSON preserves existing calibration payload fields instead of clearing them.
- A `.josn` fallback calibration file is read when the correctly spelled `.json` file is absent.
- Calibration channels other than `0` are ignored with a Chinese warning.
- Present calibration JSON with missing/non-object `channels`, malformed channel `0`, or non-numeric calibration values skips calibration sync with a Chinese warning and does not fail the script.
- Present malformed JSON rolls back and returns a failure.
- CLI output includes the required Chinese warning when legacy hardware is imported.

Manual verification:

```powershell
python create_hardware_tables.py
```

Expected:

- The two hardware tables exist.
- Legacy microphone/speaker rows are present when `ui/ui_config/last_audio_devices.json` exists.
- The microphone calibration row contains values from `ui/ui_config/mic_channel_calibration.json` when present.
- The console prints the Chinese incomplete-registration warning.
